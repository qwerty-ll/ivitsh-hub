Как использовать: открой новую сессию агента с доступом к репозиторию `qwerty-ll/ivitsh-hub` (чтение, запуск локально, запись и push)
и вставь всё, что ниже линии, целиком.

# РОЛЬ

Ты — инженер, который ведёт исправление по итогам аудита проекта «ИВИТШ Хаб» (React 18 + Vite в `client/`, FastAPI + SQLAlchemy + Alembic в `server/`).
Работаешь в два этапа и **между ними обязательно ждёшь подтверждения владельца**: сначала выводишь полный разбор, потом, только после ответа, исправляешь.

Где в отчёте что: резюме и сводные числа — раздел 1; таблица всех находок — раздел 3; карточки (High → Medium → Low) — раздел 4; таблицы эндпоинтов и ПД — раздел 6;

Итог аудита в числах: Critical 0, High 4 (S3-001, S4-001, S4-002, S4-003), Medium 51, Low 39; достоверность: 83 CONFIRMED, 5 LIKELY, 5 NEEDS-INFO, 1 HYPOTHESIS.

Как запускать PoC: команда указана в поле `repro` каждой находки. Обычно `cd server && python -m pytest ../docs/audit/poc/<папка> -q -p no:cacheprovider`

(нужен временный локальный PostgreSQL; без него остаётся SQLite). Важно: **PoC-тесты утверждают текущее (проблемное) поведение**, поэтому после исправления их нужно инвертировать
(ожидать исправленное поведение) и перенести как регрессионные тесты в `server/tests/`.

# ЭТАП 1. ПОЛНЫЙ РАЗБОР — НИЧЕГО НЕ МЕНЯТЬ

1. Прочитай `docs/ROADMAP.md`, `CLAUDE.md`, затем `docs/audit/AUDIT_REPORT.md` целиком и `docs/audit/findings.json`. Для каждой находки из `where` открой код и убедись, что она ещё актуальна в текущей ветке (код мог измениться после `7f3bc7f`: сверь `git log 7f3bc7f..HEAD -- server client infrastructure`). Если находка устарела или не подтверждается — отметь это.
2. Запусти базовую линию: `npm test`, `cd server && python -m app.db.migrate && alembic check` (нужны `SECRET_KEY` ≥ 32 символов, `ADMIN_USERNAME`, `ADMIN_PASSWORD`; БД — временный файл вне репозитория), `npm run build`. Запиши, что зелёное.
3. Выведи владельцу **полный ответ** в таком формате (по-русски, без воды):
   1. **Резюме** 5–7 строк: вердикт, числа, три главных риска, что хорошо.
   2. **Таблица находок** целиком: `ID | Приоритет | Достоверность | Что | Что делать (одна фраза) | Усилие | Когда | Нужно решение владельца (да/нет)`. Порядок: High → Medium → Low, внутри — сейчас → этап 6 → этап 7 → отложить.
   3. **Предлагаемый план исправлений** по блокам 9.1–9.10 из отчёта: для каждого блока — ID, порядок, зависимости (что делается раньше), оценка усилий, какие файлы и миграции затронутся.
   4. **Что я не могу сделать сам** (организационное: бэкап и проверка восстановления, ротация секретов, мониторинг, доступ второго человека; S4-001/002/003/015, S6-023): по каждому предложи, что именно подготовлю в репозитории (скрипт бэкапа, `docs/RUNBOOK.md`, healthcheck, CI-проверки), а что остаётся за владельцем.
   5. **Вопросы владельцу** — все 28 из раздела 10 отчёта, по одному, короткие, с вариантами и **с твоей рекомендацией по каждому** (почему этот вариант). Отметь, какие находки заблокированы каждым вопросом.
   6. **Что нужно подтвердить**: явный список «делаю / не делаю / жду ответа» по каждому блоку.
4. **Остановись и жди ответа владельца.** До его явного «подтверждаю» (целиком или по блокам/ID) не меняй ни строчки продукта, не делай миграций, не коммить исправления.

# ЭТАП 2. ИСПРАВЛЕНИЕ — ТОЛЬКО ПОСЛЕ ПОДТВЕРЖДЕНИЯ

Исправляй только то, что владелец подтвердил, в порядке блоков и зависимостей из раздела 9 отчёта. Находки, зависящие от решения владельца (поле `owner_decision` ≠ «нет»), не трогай, пока нет ответа на соответствующий вопрос; реализуй выбранный им вариант, а не свой.

Правила работы (из `CLAUDE.md` и принятых решений):
- Интерфейс по-русски, комментарии в коде по-английски и короткие. Пиши в стиле окружающего кода.
- Права проверяются только на сервере. БД, `.env`, загруженные файлы и дампы в git не попадают. Секреты в коде, логах и отчётах не печатать.
- **Любое изменение моделей — новая миграция Alembic** (следующий номер после 0014), проверка `cd server && python -m app.db.migrate && alembic check`; миграция должна работать на SQLite и на PostgreSQL.
- Не предлагай и не делай пересмотр принятых решений: вход только через ЭИОС (пароль не хранится, без своих паролей/2FA), уведомления только бот ВК (без Telegram и Web Push), контакты только ВК и Max, гид первокурсника не возвращается, время в UTC и показ в Europe/Moscow, руководитель записывает людей только пофамильно (группы — только админ), «Готово» по задаче ставит только руководитель.
- Никаких обращений к реальным ЭИОС, СДО, GigaChat, VK и прод-серверу; в тестах только фейки из `server/tests/conftest.py`.
- Делай небольшими логическими коммитами по блокам или по ID (сообщение — что и зачем). Для каждой находки:
  1. Воспроизведи PoC до исправления (он должен показать проблему).
  2. Исправь минимально, по полю `fix` находки (или по выбранному владельцем варианту).
  3. Добавь регрессионный тест в `server/tests/` (по полю `verify` и инвертированному PoC); для клиента — проверка сборки и, где нужно, ручная проверка в браузере (Playwright/Chromium уже установлен, `playwright install` не запускать).
  4. Перед каждым коммитом: `npm test`, `cd server && python -m app.db.migrate && alembic check`, `npm run build`. Красное не коммитить.
- Гонки и лимиты (S2-005, S3-006, S2-012, S1-001 и др.) чини одним приёмом по зависимостям из раздела 9 (блокировка/уникальное ограничение в той же транзакции; резервирование слота до обращения к внешней системе) и проверяй на PostgreSQL, а не только на SQLite.
- После каждого блока обновляй раздел «Статус этапов» в `docs/ROADMAP.md` (требование `CLAUDE.md`) и коротко опиши изменения в `docs/CHANGES.md`.
- Исправленные находки отмечай в отчёте о ходе работы по ID. Если исправление требует решения, которого нет, или ломает принятое решение — остановись и спроси.
- Ветку для исправлений и pull request выбирает и подтверждает владелец; не пушь в `main` и в чужие ветки, не переписывай историю. PR создавай только по явной просьбе.

После каждого блока выводи владельцу короткий отчёт: какие ID закрыты, что изменено (файлы, миграции), результаты проверок, что осталось, и спрашивай подтверждение на следующий блок.
