## 1. Итог в двух абзацах

**Сильное:** права проверяются на сервере и выдерживают атаки; гонки при брони и покупках закрыты; CSRF, загрузки,
пароль ЭИОС (не хранится), зависимости Python — в порядке; скорость на 2,5 тыс. студентов хорошая (5–70 мс).

**Слабое:** (а) несколько настоящих багов (блокировка входа чужими попытками, 500 на больших ID, админка видит 100 из
2 533 пользователей, каскадное стирание истории при удалении студента); (б) **не построено то, ради чего портал задумывался** —
уведомления (этап 6) и статистика/дашборды (этап 7): данные собираются, но не выводятся; (в) заметная перегрузка —
геймификация, 13 пунктов меню, длинный профиль, админ-функции в пяти местах.

## 2. Баги и ошибки (подтверждены)

Серьёзность: **Средняя** — мешает работе или даёт злоупотребить; **Низкая** — неудобство или защита «на будущее».

### B1. Главного администратора можно запереть чужими попытками — **Средняя**

- **Что:** 5 неверных паролей от кого угодно блокируют вход админа на 15 минут — **даже если потом ввести верный пароль**.
- **Воспроизведено вживую:** 7 запросов `POST /api/v1/auth/admin-login` с неверным паролем → ответы `[401,401,401,401,401,429,429]`;
  затем вход с **верным** паролем → `429`.
- **Причина:** `server/app/routers/auth.py:59-61` проверяет лимит по ключу `admin:<логин>` **до** проверки пароля;
  счётчик растёт от любых неудач (`rate_limit.py:75-77`: 5 попыток / 15 мин на логин, 10 / 15 мин на IP).
  Логин админа известен (виден в интерфейсе).
- **Тот же механизм у студентов (по коду, вживую не проверено):** `auth.py:132-134`, ключ `eios:<логин>` — одногруппник,
  зная логин ЭИОС, может 5 раз ввести неверный пароль и закрыть вход жертве на 15 минут.
- **Риск:** админ не может зайти, чтобы остановить атаку или обслужить портал; цель для травли студентов.
- **Как чинить:** считать неудачи по паре (логин, IP), а не по одному логину; для админа проверять пароль до применения
  лимита по логину (лимит оставить по IP); либо сообщать о блокировке и давать обход через переменную окружения.

### B2. HTTP 500 вместо 404 на больших числовых ID — **Низкая/Средняя**

- **Что:** путь вида `/api/v1/events/1180591620717411303424` даёт `500 Internal Server Error` с трейсом
  `OverflowError: Python int too large to convert to SQLite INTEGER`.
- **Масштаб:** ~45 эндпоинтов (все `{…_id}` в пути: задачи, события, вложения, форум, брони, магазин, объединения и т. д.).
  Фаззинг 3 041 запроса: **других причин 5xx нет** (кривые тела запросов обрабатываются корректно — 422).
- **На PostgreSQL (по коду, не измерено):** колонки `integer` → порог 2³¹−1, то есть упадёт уже на `99999999999`
  (`psycopg2 DataError: integer out of range`), а не только на 2⁷⁰.
- **Риск:** шум в логах и мониторинге ошибок, возможность забивать логи; не уязвимость данных.
- **Как чинить:** ограничить параметры пути (`Path(..., ge=1, le=2_147_483_647)`) или общий обработчик
  `OverflowError`/`DataError` → 404.

### B3. Админка видит только 100 из 2 533 пользователей — **Средняя**

- **Что:** вкладка «Пользователи» грузит первую страницу (`AdminPanel.jsx:50`, `api.js:179` — `limit=100`), без постраничности,
  **без поиска, фильтров и сортировки**. Счётчик на вкладке показывает «100» — выглядит как итог.
- **То же с форумом:** вкладка «Модерация форума» — «50» при 600 вопросах (лимит 50 без «ещё»).
- **Скриншот-проверка:** `Пользователи 100`, 100 строк в `<tbody>`, порядок — новые первыми.
- **Серверная сторона:** `server/app/routers/admin.py:33-49` — при поиске (`q`) загружаются **все** пользователи в память и
  фильтруются в Python; при 5 тыс. студентов это становится медленным. Поиск есть в API (`api.js:182`), но на самой вкладке его нет.
- **Риск:** администратор не может найти, заблокировать или выдать роль нужному студенту, если он не среди последних 100.
- **Как чинить:** серверный поиск/фильтр/сортировка (по группе, ФИО, курсу, активности), пагинация, честные счётчики.
  Это же — часть этапа 7 (единый список студентов с выгрузкой).

### B4. Удаление студента каскадом стирает историю — **Средняя**

- **Что:** `DELETE /api/v1/admin/users/{id}` у пользователя с данными вернул `200`; после этого в БД не осталось ни его
  **заказов магазина**, ни его **броней**, ни его **вопросов на форуме** (вместе с чужими ответами под ними).
  (Мероприятие, созданное им, осталось — `created_by` обнуляется.)
- **Риск:** теряется история выдачи мерча и броней — нечем сверяться при спорах; возврат бит и остатков не фиксируется.
  Нет «мягкого» удаления/анонимизации.
- **Как чинить:** анонимизировать (имя → «Удалённый пользователь», снять контакты и ВК), сохранив заказы/брони/форум;
  жёсткое удаление — отдельным действием с подтверждением.

### B5. Сервер не фильтрует `max_contact` — **Низкая**

- **Что:** `PATCH /api/v1/auth/me {"max_contact": "javascript:alert(1)"}` → `200`, значение сохраняется.
  (`vk_url`, наоборот, валидируется: `javascript:` и `<img …>` дают 422.)
- **Сейчас безопасно:** клиент выводит значение как текст, если оно не `https://max.ru/…`
  (`client/src/components/ContactLinks.jsx:7`) — XSS нет.
- **Риск:** «защита держится только на клиенте»; если когда-то поле начнут выводить как ссылку — станет дырой.
- **Как чинить:** та же валидация на сервере, что и у `vk_url`.

### B6. Проверка загруженных файлов — только по первым байтам — **Низкая**

- **Что:** `server/app/services/uploads.py:39-42` сверяет лишь сигнатуру. Файл `x.png` с телом
  `\x89PNG\r\n\x1a\n<script>alert(1)</script>` принят (`201`). Имена `../../etc/passwd.pdf` и `a.php.pdf` — приняты, но имя
  очищается до `passwd.pdf` и хранится под случайным `uuid`.
- **Почему не опасно:** отдача всегда `Content-Disposition: attachment` + `X-Content-Type-Options: nosniff`
  (`attachments.py:209-214`), хранение вне веб-корня. Проверено скачиванием.
- **Риск:** низкий; замечание на «будущее» (антивирус, перекодирование изображений, если файлы начнут показывать inline).

### B7. Одна низкая уязвимость в зависимости — **Низкая**

- `npm audit --omit=dev`: **DOMPurify** — `IN_PLACE` с хуком `afterSanitize` (GHSA-p98j-92pf-mc4p), 1 low.
  Проект вызывает обычный `DOMPurify.sanitize(...)` (`FaqPage.jsx:40`, `AdminPanel.jsx:820`) — режим не используется,
  **не эксплуатируется**. Лечится `npm audit fix`.
- `pip-audit -r server/requirements.txt`: **уязвимостей нет**.

### B8. Мелкие дефекты интерфейса — **Низкая**

- **Баннер cookie закрывает контент на телефоне** («Мои задачи», кнопки) до нажатия «Понятно»
  (снимки `m1-mobile-_`, `m1-mobile-_calendar`).
- **Консоль у гостя:** на каждой странице красная ошибка `401 (Unauthorized)` — это `GET /auth/me` для неавторизованного;
  функционально безвредно, но засоряет консоль и мониторинг.
- **Гость видит в боковом меню «Календарь», «Задачи», «Мероприятия»**, которые без входа бесполезны
  (в нижней панели телефона «Календарь» для гостя уже подменён на «Расписание» — на десктопе нет).
- **Фото профиля хранится только в браузере** (текст на странице профиля: «на другом устройстве выберите его снова»).
- **Профиль на телефоне — 3 061 px прокрутки** (достижения, ПГАС/портфолио, контакты, фото в одной странице).

## 4. Чего не хватает

### Функционально (по ROADMAP и по логике продукта)

1. **Нет уведомлений вообще** (этап 6 отложен). Ни ВК, ни почты, ни push, ни iCal; в коде нет ни одного механизма
   доставки (`grep`: `smtp`, `vk_user_id`, `icalendar` — пусто). Студент узнаёт о задаче, решении по заявке, отмене брони,
   новом объявлении **только открыв портал**. Для портала, чья ценность — связь «руководитель ↔ участник», это главная дыра.
   *Дёшево до ВК:* индикатор «новое» в интерфейсе и iCal-подписка на календарь.
2. **Нет статистики и отчётности** (этап 7 не начат). Данные собираются, но **нигде не выводятся**:
   - `users.last_seen_at` пишется (`security.py:124-140`) и **не читается нигде** в коде;
   - `task_assignees.completed_at`, посещаемость собраний и мероприятий — только в личные «биты», не в отчёты.
   Отсутствуют: единый список студентов с сортировкой по группе/ФИО и выгрузкой; активность по курсам;
   **выгрузка участников объединения** (ни админу, ни руководителю — в API нет такого эндпоинта); дашборд руководителя
   (сколько собраний посетил, сколько просрочил); популярность мероприятий.
3. **ВИТШик не знает новых разделов.** Функции агента: `schedule`, `find_room`, `find_teacher`, `search_portal`
   (`services/agent.py`). Про задачи, собрания, мероприятия, бронь, ДЗ группы — ничего (в ROADMAP это отмечено как «позже»).
4. **Бронь 108:** нет повторяющихся броней (еженедельное собрание = 10 отдельных броней при лимите 10 предстоящих);
   собрание не связано с бронью (место — просто текст); нет подтверждения и приоритетов — действует «кто первый»;
   каждый руководитель может держать до 10 × 6 часов, спор решает только админ.
5. **Нет листа ожидания** у мероприятий с лимитом.
6. **Нет самообслуживания данных:** удалить аккаунт и отозвать согласие ПД — только письмом в дирекцию
   (описано в политике, допустимо, но вручную).
7. **Нет журнала действий администраторов** (см. R10).
8. **Нет роли старосты**, «Гайдов по документам» и новостной ленты (этап 8 — по плану).
9. **Ручной правки сопоставления курсов СДО с дисциплинами у админа нет** (отмечено в ROADMAP, этап 3).
10. **Не вошедшие через ЭИОС не попадают в портал вообще** (выпускники, преподаватели, внешние) — только режим «гость».

## 6. Что проверено и работает

- **Права на сервере.** Из ~30 попыток (чужой руководитель, не-участник, участник без прав, другая группа) — ни одна не прошла.
  Чужие задачи/файлы/события/собрания отвечают **404** (существование не раскрывается), чужое управление — **403**.
  Ответ `GET /associations/{id}` для посторонних: `members`, `applications`, `removed` — пустые.
  Ответ события для обычного участника: список записавшихся — пуст (видно только число).
  Анонимам закрыт весь личный контент (401); открыты только публичные справочники.
- **Повышение прав:** `PATCH /auth/me` с `role`/`full_name`/`is_blocked` — игнорируется; смена роли, бит-гранты, запись групп,
  создание мероприятий института — только админ.
- **Гонки:** 20 параллельных броней одного слота → ровно 1 успех; ноутбуки (всего 5): 10 запросов по 2 → ровно 2 успеха;
  30 покупок последней единицы → ровно 1; 10 параллельных трат одного баланса (100 бит, цена 60) → ровно 1, баланс 40.
- **CSRF:** запись с cookie без `X-Requested-With` → 403 (включая загрузку файлов и form-encoded).
- **Блокировка пользователя:** после блокировки токен немедленно даёт 401. Выход отзывает токен.
- **Ссылки:** `javascript:`, `data:`, `vbscript:`, `//evil`, `ftp:` в ссылках задач — 422.
- **Пароль ЭИОС/СДО:** не сохраняется и не логируется (`sdo.py`, `auth.py`); проверка SSL включена по умолчанию.
- **Валидация тел запросов:** `null`, `[]`, 100 000 символов, вложенные типы — 422/400, не 500.
- **Файлы:** подпись + размер (10 МБ → 413), пустой файл → 400, SVG/exe → 415, квота и лимит на объект.
- **Скорость на 2 533 студентах** (медиана 5 запусков, SQLite): `/associations` 43–48 мс, `/forum/questions` 13 мс,
  `/progress` 13 мс, `/shop` 11 мс, `/tasks/my` 8 мс, `/admin/users` 12 мс, `/admin/associations` 65 мс.
- **Сборка** `npm run build` проходит за ~6 с; ошибок JS в консоли нет (кроме 401 у гостя, см. B8).

## 7. Что проверил и снял (не баги)

- **«Админ выкидывается на главную при обновлении `/admin`»** — артефакт теста: в чистом браузере не было кэша профиля
  в `localStorage`; у реального пользователя он есть после входа (`AuthContext.jsx`).
  Пограничный случай: очистка только localStorage при живой cookie.
- **«Версия согласия ПД не обновлена после новых разделов»** — не проблема: текст политики менялся в один день (`2026-09-30`),
  а согласие запрашивается и перезаписывается при **каждом** входе.
- **«Топ трайбов с ФИО — утечка»** — это описанное в политике решение («все вошедшие видят состав трайбов с ФИО, группой и
  очками лучших участников»). Но противоречит ROADMAP §8.1 («рейтинг только по желанию студента») — вопрос к автору.
- **DOMPurify** — см. B7, не эксплуатируется.

## 9. Приложение: как воспроизвести ключевые баги

**B1 (блокировка админа):**
```bash
for i in 1 2 3 4 5 6; do
  curl -s -o /dev/null -w "%{http_code} " -X POST localhost:8000/api/v1/auth/admin-login \
    -H 'Content-Type: application/json' -H 'X-Requested-With: XMLHttpRequest' \
    -d '{"username":"<ADMIN_USERNAME>","password":"wrong"}'
done
# 401 401 401 401 401 429 — затем вход с верным паролем тоже даст 429 на 15 минут
```

**B2 (500 на большом ID):**
```bash
curl -i -b 'portal_token=<token>' localhost:8000/api/v1/events/1180591620717411303424
# HTTP/1.1 500 Internal Server Error  (на PostgreSQL — уже при 99999999999)
```

**B3 (админка):** войти админом → «Панель управления» → «Пользователи»: 100 строк при 2 533 пользователях в БД, поиска нет.

**B4 (каскад):** создать пользователя с заказом в магазине, бронью и вопросом на форуме →
`DELETE /api/v1/admin/users/{id}` → в БД не остаётся его `shop_orders`, `bookings`, `forum_questions`.

**B5:**
```bash
curl -X PATCH -b 'portal_token=<token>' -H 'X-Requested-With: XMLHttpRequest' -H 'Content-Type: application/json' \
  -d '{"max_contact":"javascript:alert(1)"}' localhost:8000/api/v1/auth/me   # 200, значение сохранено
```
